服务凭什么证明“我是我”——工作负载身份入门(上)

Posted on 日 02 8月 2026 in Tech

Abstract 服务凭什么证明“我是我”——工作负载身份入门(上)
Authors Walter Fan
Category learning note
Status v1.0
Updated 2026-08-02

咱们先想一个特别朴素的问题。

你写了个订单服务,部署上线,半夜它要去连数据库、要去调支付服务、要去内部的消息队列里丢一条消息。每一步对方都会问同一句话:你是谁?凭什么让你进来?

人登录靠账号密码、靠短信验证码、靠人脸;那服务呢?服务没有手指按不了指纹,它半夜三点也没人盯着帮它输密码。一个没有人值守的程序,怎么向另一个程序证明自己的身份? 这就是“工作负载身份(Workload Identity)”要解决的事——这里的“工作负载”你就理解成“一个跑起来的服务实例”,VM 也好、容器也好、一个进程也好,都算。

这篇文章想说清楚一件事:很多团队今天的做法,是把服务的身份隐式地寄生在别的东西上——最典型的就是云厂商的 IAM 角色加一大坨长期密钥。这套能跑,但它把身份、密钥、云、权限焊死在一起,像滚雪球一样越滚越重。而业界早有一套更干净的标准解法,叫 SPIFFE。看完你会明白:把“身份”从“密钥”和“云”里拆出来单独管,是后面一切安全改造的地基。

提示:文中 IAM、CA、证书、JWT、SVID 这些词,第一次出现我都会用一句大白话解释。不熟悉云和 OAuth 的读者也能顺下来,代码块可以跳过。

1. 先看看今天大多数人是怎么“凑合”的

服务要证明身份,现实里最常见的一招,是借云厂商的力。

以 AWS 为例(其它云思路一样)。你给服务分配一个 IAM 角色——你可以把 IAM 角色理解成云上的“工牌”,上面写着“持这张牌的人可以读这个数据库、可以往那个桶里写文件”。服务跑起来后,自动拿到这张工牌,拿着它去访问云资源,一切顺理成章。

那服务要访问的密钥(数据库密码、第三方 API key、签名用的私钥)放哪呢?通常是放进一个密钥管理系统里,而这个系统又用 IAM 角色来判断“谁能取哪些密钥”。于是就形成了一个隐式的等式:

一个独一无二的 IAM 角色 = 一份独一无二的密钥访问权限 = 事实上的一个服务身份。

换句话说,你从来没有显式地给服务发过“身份证”,但那个 IAM 角色本身,就被当成了身份证在用。 举个具化的例子,某个角色的名字可能长这样:

arn:aws:iam::123456789012:role/secrets@dev_ordersvc_us_us01

（这里的账号 ID、服务名、集群名我都换成了占位符。）从这串字符里其实能读出一堆信息:环境是 dev、应用是 ordersvc、集群是 us/us01。这些信息,恰恰就是“这个服务是谁”的全部内容。

看到这你可能会说:那不挺好吗?能跑、信息也全。

问题恰恰在这——它把太多东西焊在了一起。

2. 焊死在一起,到底坏在哪

这套“隐式身份”方案,平时风平浪静,一旦你想往前走一步,四面都是墙。我把它的耦合拆成四条,你对号入座一下:

耦合维度 具体表现 一旦想改就麻烦在哪
锁死单一层级 身份被硬编进 {环境}/{应用}/{集群} 这种固定路径 换个维度切分(比如按 region、按租户)就得重构整棵树
和密钥系统深度绑定 身份逻辑长在密钥管理系统里 密钥系统背了太多安全责任,牵一发动全身
和密钥本身绑定 “有身份”约等于“能取密钥” 想只认证不取密钥?对不起,这俩分不开
锁死单一云 身份就是 AWS IAM 角色 想上第二朵云、想混合部署?身份体系整个搬不动

我挑最扎心的两条展开讲。

第一,身份和云被焊死了。 你的身份就是 AWS 的 IAM 角色,那这套东西天生只认 AWS。哪天业务要扩到第二朵云,或者要在自己机房里跑一部分,你会发现“身份”这个最底层的概念根本搬不过去——因为它压根不是一个独立的东西,它是 AWS 的一个内部对象。这就像你把全部家当都存在一家银行,并且这家银行的存折只能在这家用,换个城市连门都进不去。

第二,责任全压给了密钥系统。 本来密钥管理系统的活儿是“安全地保管和分发密钥”,结果因为身份逻辑长在它身上,它顺带还管了“谁是谁”“谁能访问谁”。一个系统扛了三份责任,它的爆炸半径(blast radius,意思是“一旦它出事,能波及多大范围”)就大得吓人。安全工程里有条朴素原则:一个组件的职责越单一,它出问题时你越好收拾。 把身份从密钥系统里剥出来,本身就是一次减负。

一句话总结这一节:

今天很多团队的“服务身份”,不是设计出来的,是从 IAM 角色里长出来的。能用,但它把身份、密钥、云、权限四样东西拧成了一股绳,想解开任何一样,都得动全身。

3. 业界标准解法:SPIFFE 和它的“身份证”SVID

那正经的做法长什么样?答案是把身份当成一等公民,单独发、单独管。这方面有现成的开放标准,叫 SPIFFE(Secure Production Identity Framework For Everyone,面向所有人的生产环境安全身份框架,CNCF 旗下项目)。名字很长,核心思想一句话:

每一个工作负载,都应该拿到一张由可信机构签发的、短时效的、可自动轮换的“数字身份证”。

这张身份证,SPIFFE 里叫 SVID(SPIFFE Verifiable Identity Document,SPIFFE 可验证身份文档)。你先别被缩写吓到,它本质就是一份文件——要么是一张 X.509 证书,要么是一个 JWT(JSON Web Token,一种带签名、能自证真伪的小令牌)。这份文件上写着这个服务是谁,并且带着一个可信机构的签名。

它有三个关键性质,恰好把上一节的坑全填了:

  • 短时效(TTL 很短):身份证不是发一次管一辈子,而是几分钟、几小时就过期。想活得久,就得不停去续。
  • 自动轮换:续签这件事交给工具链自动干,应用自己不用操心。私钥泄露了?过几分钟自动换一把,损失被压到最小。
  • 可验证:签名能一路往上追溯,最终追到一个你信任的根——一个专门用于服务身份的内部 CA(Certificate Authority,证书颁发机构,你就理解成“盖权威公章的地方”)。谁拿着这张证,别人一验签就知道真假。

发身份证这件事,现在有成熟的工具链能干(比如 SPIFFE 的参考实现 SPIRE,以及一些商业方案)。典型的做法是:每台机器上跑一个小小的 agent,它负责替本机上的服务去申请身份证、把身份证放到磁盘上或者通过一个本地 socket 递给应用,并且在快过期时悄悄换上新的。应用侧再配个 SDK,负责把身份证和对应的密钥对读进内存。整个过程,应用几乎无感。

4. 身份证上该写什么

现在轮到最实在的问题:这张身份证上,到底该印哪些字段?

原则是:印上任何“别人需要据此判断你是谁、要不要放你进来”的信息。 对绝大多数后端系统,下面这几个是通用的:

  • application(应用):比如 ordersvc、paysvc、mq。这是最核心的一维——你是哪个服务。
  • environment(环境):prod(生产)/ staging(预发)/ dev(开发)。生产环境的订单服务和开发环境的订单服务,绝对不能被当成同一个身份。
  • cluster(集群):服务跑在哪个集群。
  • region(区域):跑在哪个地理区域。

有意思的是,你回头看第 1 节那串 IAM 角色的名字——dev_ordersvc_us_us01——它其实装的是一模一样的信息!环境、应用、集群,一个不少。

那新老两套方案的差别到底在哪?就在于:

隐式(藏在 IAM 角色里) 显式(SPIFFE 身份证)
信息载体 一串角色名,只能靠约定解析 结构化字段,机器直接读
层级 死锁在 环境/应用/集群 想加维度就加,不受路径约束
归谁管 密钥系统 独立的身份服务
绑不绑密钥 绑死(有身份≈能取密钥) 解耦(身份归身份,密钥归密钥)
跨不跨云 只认一朵云 云中立

同样的信息,一个是从角色名里“猜”出来的,一个是明明白白结构化印在证件上、还盖了公章的。前者是副产品,后者是设计。这就是“隐式”和“显式”最根本的区别。

5. 拆开之后,天地就宽了

一旦身份成了独立的一等公民,好几件原本很别扭的事,突然就顺了。

第一,身份可以用来换权限,而不是等于权限。 服务先证明“我是生产环境的订单服务”,再拿这个证明去换一张云上的 IAM 工牌、或者去取密钥、或者去调用别的内部服务。注意顺序变了:先有身份,再谈授权。 而不是像以前那样,身份和权限是同一个东西。

第二,密钥系统可以“瘦身”了。 身份逻辑搬走之后,密钥系统回归本职:安全地存、安全地发。责任单一,爆炸半径小,安全团队睡得着觉。

第三,多云、混合云不再是天堑。 身份是一份自证真伪的文件,不依赖任何一朵云。你在 AWS、在别的云、在自己机房,拿的都是同一种身份证,验签逻辑也一样。

第四,它给“服务间认证”铺好了地基。 这是我最想强调的一点,也是下一篇的主题。你想想:如果每个服务都已经握着一张带公钥的身份证、手里还攥着对应的私钥,那“A 服务向 B 服务证明自己、B 反过来也能确认 A”这件事,几乎是顺手就能搭上去的——地基打好了,盖房子就快了。

最后一句

回到开头那个朴素的问题:一个没人值守的服务,半夜怎么证明自己是谁?

别让它去“借”身份——借云厂商的 IAM 角色、借一坨长期密钥。给它发一张真正属于它自己的、短命的、能自证真伪的身份证。 身份、密钥、云、权限,这四样东西该各归各位。焊在一起省事一时,拆开来才走得远。

下一篇咱们接着往下走:身份证有了,证书和 JWT 到底该选哪个来做服务间认证?这背后是一场 L4 与 L7、mTLS 与 JWT 的经典架构之争——没有标准答案,只有取舍。
