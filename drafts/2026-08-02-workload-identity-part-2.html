证书还是 JWT?服务间认证的 L4 与 L7 之争——工作负载身份入门(中)

Posted on 日 02 8月 2026 in Tech

上一篇咱们把地基打好了:每个服务都能拿到一张短命的、可自证真伪的身份证(SPIFFE 里叫 SVID)。文章结尾我留了个尾巴——身份证有了,拿它给服务间通信做认证,几乎是顺手的事。

但“顺手”不代表“只有一条路”。恰恰相反,这里有一个很容易站队、也很容易站错队的选择:

拿到身份之后,服务 A 向服务 B 证明自己,是走 TLS 层的 mTLS(靠证书),还是走应用层的 JWT(靠令牌)?

我见过不少团队在这上面吵得面红耳赤,一方觉得“mTLS 才是零信任正统,不上就是不安全”,另一方觉得“JWT 我们熟得很,别折腾”。吵到最后往往是谁嗓门大谁赢——这是最糟的决策方式。

这篇想说清楚:这不是一道技术优劣题,是一道架构取舍题。 mTLS 更“正统”,但正统不等于此时此地更划算。我会重点拆一个特别容易被忽略的坑——非线性 rollout 陷阱,它是很多工程主导的团队最终先选 JWT 的真正原因。

提示:L4、L7、mTLS、bearer token 这些词第一次出现我都会用大白话解释。不熟网络分层的读者也能顺下来。

1. 先分清楚:你在哪一层证明身份

要理解这场争论,得先有个坐标。网络世界习惯用“L几”来说“在哪一层干活”,咱们只需要记住两层:

  • L4(传输层):大致对应 TCP/TLS 这一层。mTLS 就在这里。 它在“建立连接、握手”的时候就把身份验了,验完之后这条管道里流的所有数据都自带信任。
  • L7(应用层):HTTP 这一层。JWT 就在这里。 连接怎么建的它不管,它是在每个 HTTP 请求里塞一个令牌来证明身份。

打个生活里的比方:

  • mTLS 像进门时刷工牌。 你和保安互相验证(你验保安是真保安,保安验你是真员工——这就是“互相”,mutual 的意思),门一开,进去之后楼里随便走,没人再拦你。
  • JWT 像每递一份文件都附一张签名条。 门可能是虚掩的,但你每次办事都得出示一张“我是谁、这事我经手”的凭条。

一个在连接层面一次性把关,一个在每次请求上反复证明。记住这个画面,下面就好懂了。

2. mTLS:更“正统”,好在哪

先说 mTLS(mutual TLS,双向 TLS)。普通 HTTPS 只有服务器出示证书、客户端验证;mTLS 是双方都出示证书、互相验证。上一篇说的那张身份证,如果是 X.509 证书形态,天生就能插进 mTLS。

它的好处很实在:

  • 极其标准,生态成熟。 TLS 是几十年的老技术,工具、库、云服务开箱即用,不用你造轮子。比如你可以用证书去换云上的 IAM 工牌(AWS 的 IAM Roles Anywhere 就是干这个的),整条链路都是现成的。
  • 证书是“对公钥的可信签名”。 这句话有点抽象,我拆开说:Alice 有一对公私钥,她的证书就是一个权威机构盖章说“这把公钥确实是 Alice 的”。于是 Bob 验过证书后,Alice 就能用私钥给 Bob 发可验证是本人发的消息。这是个很强的密码学原语,能玩出很多花样。
  • 网络层安全,一步到位。 这是 mTLS 最诱人的地方。如果全公司所有服务之间都强制走 mTLS,那网络层面的安全水位会整体抬升一大截——理想状态下,内部服务之间只用 mTLS 说话,谁都别想在网络里冒充别人、偷听别人。很多公司的内网安全恰恰是短板,mTLS 是补这块短板的正解。

听起来近乎完美,对吧?那为什么不是所有人都上?

3. mTLS 的现实阻力:那个致命的“非线性”

问题不在 mTLS 本身,在落地。我先把话撂这:

mTLS 的价值,只有当“接收方强制要求所有人都用 mTLS”时才真正兑现。

这句话是整篇文章的题眼,值得嚼一嚼。

假设 Alice 想用 mTLS 和 Bob 通信。Alice 单方面把 mTLS 配好了——然后呢?只要 Bob 还允许别人用普通方式连它(为了兼容那些还没改造的老服务),那攻击者照样能绕过 mTLS 直接敲 Bob 的门。Alice 那边的 mTLS,安全收益基本是零。

真正的收益,发生在 Bob 硬起心肠、拒绝一切非 mTLS 连接的那一刻。可 Bob 敢这么做的前提是——所有会调用 Bob 的服务都已经改造完了。哪怕漏一个,Bob 一硬,那个服务当场就挂。

于是你就撞上了这个陷阱:

mTLS 的 rollout 不是线性的。 你得先把绝大部分服务都改造完(前期投入巨大、期间没有任何安全收益),直到某个临界点接收方敢强制开启,收益才“啪”地一下出现。

这跟修桥一个道理:桥修到 99%,通车收益还是零,因为没人能过河;非得等最后 1% 合龙,价值才一次性释放。

对网络拓扑本身就统一、干净的公司(比如生来就全跑在 k8s、部署高度一致),这个坎没那么高。但对网络异构的公司——服务散落在机房、多云、各种历史部署形态里——想让所有服务都强制 mTLS,难到几乎无从下手。这也正是很多公司内网安全一直是短板的根本原因:不是不想上 mTLS,是这条非线性的路太长、太贵、中途看不到回报,没人扛得住。

4. 那 JWT 呢?工程主导的团队为什么偏爱它

再看 JWT(JSON Web Token,一种带签名、能自证真伪的应用层令牌)。它走 L7,在每个 HTTP 请求里带令牌。相比 mTLS,它有几个特别“接地气”的优点:

  • 可以渐进式上,收益是线性的。 这是和 mTLS 最本质的区别。你不需要“所有人都改完才有收益”——两个服务今天想加认证,今天就能加,立刻见效,不用等全公司合龙。能一点点上、每一步都有回报,对工程团队太重要了。
  • 人能直接读、能 debug。 JWT 解开就是一段 JSON,谁是谁、什么时候过期、带了哪些信息,肉眼可见。半夜排障时,这种“看得见摸得着”省下的时间,谁排过谁知道。
  • 团队熟、心智负担低。 很多团队本来就在大量用 JWT(登录令牌、API 鉴权),它的安全边界、常见坑、库支持都是老熟人。引入一个大家都懂的东西,比推一个全新体系阻力小得多。
  • 它的安全取舍是“已知的”。 JWT 有它的毛病(比如 bearer token“谁拿到谁就能用”的先天问题),但这些毛病业界研究得透透的,该怎么防有成熟答案。已知的魔鬼,好过未知的天使。

这里插一句我的观察:一个团队选 mTLS 还是 JWT,常常暴露它的基因。

有些公司是 devops/平台主导的:复杂度沉在平台和基础设施里,像服务间认证这种事,理想状态是从应用代码里彻底抽走、下沉到 service mesh(服务网格)去自动搞定,应用根本不用管。这种基因,天然亲近 mTLS。

另一些公司是 工程主导的:复杂度活在应用代码、SDK、库里。对它们来说,在应用层用一个熟悉的 JWT 库把认证做掉,比推动整个基础设施转型现实得多。技术选型从来不只是技术问题,它得贴着组织的形状走。

5. 一张表,把取舍摊开

吵架没用,把牌摊桌上一条条比:

维度 mTLS(L4 / 证书) JWT(L7 / 令牌)
工作层次 传输层,连接握手时验 应用层,每个请求带令牌
标准与生态 极成熟,直接插云服务 极成熟,团队普遍在用
rollout 曲线 非线性,合龙前收益为零 线性,加一对就赚一对
网络层安全 强(理想态可堵住内网冒充/偷听) 弱(不碰网络层)
对异构网络 极难落地 容易落地
可读性/可 debug 差(TLS 层,不透明) 好(解开就是 JSON)
双向认证 天生支持 需要额外机制
适合的组织基因 devops / 平台 / 已统一到 k8s 工程主导 / 网络异构 / 渐进改造

看完这张表,结论其实不难下:

  • 如果你司网络已经很统一(比如全在 k8s、部署高度一致),又想一步到位把内网安全拉满,mTLS 值得咬牙推。
  • 如果你司网络异构、想先拿到收益再慢慢演进、团队又对 JWT 很熟,那先在 L7 用 JWT 把认证收敛起来,是更务实的第一步。

6. 我的建议:别把最大的收益,押在最难的那一步上

到这我想给个明确的立场,而不是和稀泥。

服务间认证最大的一块收益,其实是“收敛”——把原来七零八落、各写各的认证方式,统一成一套。这块收益,在 L7 用 JWT 就能拿到,不需要等 mTLS 合龙。

而 mTLS 那块额外的网络层收益,固然诱人,但它被锁在“非线性 rollout”这道最难的关卡后面。把最大的、唾手可得的收益,押注在最难、最慢、中途没回报的那一步上,是不划算的。

所以我倾向于:

先在 L7 用统一的令牌方案把服务间认证收敛掉,尽快兑现收益;把 L4 的 mTLS 留到基础设施足够统一(比如一切都跑在 k8s、走一致的部署管道)之后,再作为“下沉”动作去做。

这不是说 mTLS 不好——它很好,是终局。只是路要一步步走,先摘够得着的果子。 认证方式的选择,不该被“哪个更正统”绑架,而该被“此刻哪条路能让我持续拿到回报”牵引。

顺带说一句:这条路和上一篇的地基是咬合的——只要每个服务都握着一张带公钥的身份证,那么无论你最终选 mTLS 还是 JWT,底层都是同一套身份。先统一身份,再谈认证方式,你就有了随时切换、逐步演进的自由。

rollout 不是抽象问题

服务间认证改造最好按边界分批，而不是按“全公司一次切换”设计。可以先让接收方同时支持旧认证和新认证，再选择一条低风险调用链做旁路校验；差异清零后，才把新认证切成强制，最后关闭旧路径。

每一阶段都要有回滚条件：验证失败率、证书或 Token 刷新失败率、额外延迟、无法定位的跨团队调用。这样“mTLS 更正统”或“JWT 更容易”就不再是口水战，而是可以放进实际约束里比较的工程选项。

最后一句

mTLS 和 JWT 之争,表面是技术,里子是取舍;取舍的关键,又藏在一个反直觉的地方——rollout 是线性的还是非线性的。

能一步步上、每步都有回报的方案(JWT / L7),往往比一步到位却要死磕到合龙才见效的方案(mTLS / L4),更适合作为第一步。这不是保守,是尊重现实。

下一篇是这个系列的收官:咱们把 L7 这条路走到底,看看一个具体的协议——WIMSE,用 WIT + WPT 两个令牌,怎么把“任何服务都能确切知道是谁在跟它说话”这件事,干净利落地实现出来。

行动清单(可抄)

  • [ ] 先问自己:你司网络是统一(全 k8s)还是异构(机房/多云/历史部署混杂)?
  • [ ] 别只比“哪个更安全”,把 rollout 曲线(线性 vs 非线性)加进决策。
  • [ ] 若走 mTLS,先算清“合龙”前的投入期有多长、期间零收益能不能扛。
  • [ ] 若走 JWT,先把散落各处的认证方式收敛成一套——这是最大的一块收益。
  • [ ] 无论选哪条,先保证底层是统一的服务身份,给自己留下切换与演进的余地。
