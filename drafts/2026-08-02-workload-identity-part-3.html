WIMSE 实战:用 WIT + WPT 让每个服务都知道“在跟谁说话”——工作负载身份入门(下)

Posted on 日 02 8月 2026 in Tech

系列走到收官。前两篇搭好了台子:

  • 上篇:每个服务该有一张短命、可自证真伪的身份证(SPIFFE / SVID)。
  • 中篇:拿身份证做认证,先走 L7(JWT) 这条能渐进、能马上见效的路,别一上来就死磕 mTLS 的“合龙”。

这一篇把话讲到能动手:具体用什么协议、令牌长什么样、请求里塞什么头、接收方怎么验、授权怎么接、落地要改多少代码。主角是一个叫 WIMSE 的协议——它用两个 JWT 配合,干净利落地实现了一件事:

任何服务收到一个请求时,都能确切地知道“到底是谁在跟我说话”,而且对方偷不了、冒充不了、重放不了。

看完你会发现:如果第一篇的身份地基已经打好,那这套认证几乎是顺手搭上去的,对现有 JWT 库的改动比想象中小得多。

提示:JWT、公钥/私钥、bearer token、哈希、audience 这些词第一次出现我都用大白话解释。JSON 块看不懂可以跳过,不影响主线。

1. WIMSE 是什么:给 SPIFFE 补上“怎么用”

先给个定位。上篇讲的 SPIFFE/SVID 解决的是“怎么发身份证”。但发完之后,两个服务之间具体怎么用这张证来认证一次 HTTP 请求?这块 SPIFFE 本身讲得不细。

WIMSE(Workload Identity in Multi-System Environments,多系统环境下的工作负载身份)就是来补这一块的。它是 SPIFFE/SVID 的扩展,目前是 IETF 正在制定的草案协议——注意“草案”二字,细节以后可能微调,但主体思路已经相当成型。

它给你两样东西:

  1. 一份每个工作负载独有、有时效的身份文档,由身份服务签发。短命(想设多短设多短),里面装着你关心的所有信息:环境、区域、应用、集群……这份文档是个 JWT,名字叫 WIT(Workload Identity Token,工作负载身份令牌)。它本质就是上篇说的 SVID。
  2. 一对公私钥。工作负载自己攥着私钥,而对应的公钥被写进 WIT 里、由身份服务盖章签名。

记住这个组合:一份带公钥的身份令牌(WIT) + 一把只有你自己有的私钥。 整套协议都建在这上面。

2. WIT:服务的“数字身份证”,可以公开

先看 WIT。它是一个 JWT,长这样(字段都用中性占位,你照着理解结构就行):

{
  "iss": "wimse://example.com/prod/identity",
  "sub": "wimse://example.com/prod/ordersvc/us/us01",
  "cnf": {
    "jwk": {
      "kty": "EC",
      "crv": "P-256",
      "x": "f83OJ9TtEX6m9sZ6LPZG9J9mABzrxMQFvdyfgxwqO4",
      "y": "hKw6UsUwz39FhS_8I0-2YbdtYZh9Svh3gg8rgrq6deE",
      "alg": "ES256"
    }
  },
  "svc": {
    "env": "prod",
    "app": "ordersvc",
    "cluster": "us/us01",
    "region": "us-east-2",
    "instance-id": "i-111111111"
  }
}

逐条拆:

  1. iss(issuer,签发者):谁签发并签名了这张证。想验它真假的人,得去拿签发者的公钥,而这个公钥应该一路能追溯到你信任的内部根 CA(上篇说的“盖权威公章的地方”)。
  2. sub(subject,主体):这张证属于哪一个具体的工作负载实例——这里是生产环境、跑在 us/us01 集群某个实例上的 ordersvc。
  3. 注意:没有 aud(audience,受众)。 这点很关键。普通 JWT 我们常当 bearer token 用——谁拿到谁就能用,所以必须限定“这令牌只给某某用”(aud)。但 WIT 不是 bearer token,它更像一张 TLS 证书:证书本来就是给全世界看的,公开无所谓。 所以它不设 aud,不怕被别人看到。
  4. svc 里的业务声明:环境、应用、集群、区域、实例 ID——就是上篇说的“身份证上该印的字段”。别人靠这些来判断“你是谁、要不要放你进来”。
  5. cnf(confirmation,确认)里的 jwk:jwk 是公钥的标准表示法(JSON Web Key)。这里放的是这个工作负载的公钥,而且它被签发者签了名——等于身份服务盖章说“这把公钥确实是这个服务的”。
  6. 私钥在哪? 在工作负载自己(和本机 agent)的内存里,永不外泄。WIT 里只有公钥,私钥自己死死攥着。

一句话记住 WIT:

WIT = 一张公开的数字身份证,上面印着“我是谁”,还嵌着“我的公钥”,并由可信机构盖了章。它可以随便给人看,因为看了也冒充不了你——私钥不在证上。

3. WPT:极短命的“持有证明”,防的就是冒充和重放

光有 WIT 不够。WIT 是公开的,那我把你的 WIT 抄下来,冒充你行不行?

不行。 这就是第二个令牌 WPT(Workload Proof Token,工作负载证明令牌)存在的意义。它也是个 JWT,但由 WIT 里那把公钥对应的私钥来签名——而私钥只有你有。所以能签出有效 WPT 的,只可能是真身。

WPT 长这样:

{
  "iss": "wimse://example.com/prod/ordersvc/us/us01",
  "aud": "https://example.com/paysvc",
  "exp": 11111111111,
  "wth": "-Ji8TlMNFk3qmzmpAxBO_7W-YutcH_2_fuFAFFSV1Rg"
}

拆解:

  1. iss:发起这次请求的人——这里是那个具体的 ordersvc 实例。
  2. aud(受众):这次请求是发给谁的——这里是支付服务 paysvc。有了它,别人截获这张 WPT 也没法拿去敲别的服务的门(因为 aud 对不上)。
  3. exp(expiration,过期时间):WPT 极其短命。WIT + WPT 合起来才是真正的 bearer 凭证,而 WPT 无需任何特殊的密钥协调,它只要活得比这次请求久一点点就够——大多数场景 5 分钟绰绰有余。命越短,被人截获重放的窗口越小。
  4. wth(WIT hash,WIT 的哈希):这是把 WPT 和 WIT 牢牢绑在一起的胶水。它是 WIT 内容的一段哈希(哈希=把一大段内容压成一个固定长度的“指纹”,内容改一个字,指纹就全变)。有了它,接收方能确认“这张 WPT 说的就是这张 WIT”,两者不能被拆开拼装。

WIT 和 WPT 的分工,可以这么记:

WIT WPT
是什么 身份令牌(身份证) 证明令牌(持有证明)
谁签的 身份服务(可信 CA) 工作负载自己的私钥
里面装什么 我是谁 + 我的公钥 我要发给谁 + 何时过期 + 绑定哪张 WIT
能不能公开 能(像证书) 一次性、极短命,发完即弃
谁能造出来 只有身份服务 只有持有私钥的真身

一个证明“我是谁”(长期、公开),一个证明“这条请求真的是我此刻发的、发给你的”(临时、私签)。两张一凑,冒充和重放就都堵死了。

4. 认证一次 HTTP 请求:两个头 + 五步校验

有了这两张令牌,一次带认证的请求就特别直白。假设 ordersvc 要调 paysvc:

发起方(ordersvc)做两件事:

  1. 把自己的 WIT 放进一个头,比如叫 X-WI-WIT。
  2. 针对目标 paysvc 现签一张 WPT,放进另一个头,比如 X-WI-WPT。
sequenceDiagram
    participant O as ordersvc
    participant P as paysvc
    O->>O: 从本机 agent 取 WIT + 私钥
    O->>O: 用私钥现签一张 WPT(aud=paysvc, wth=WIT哈希)
    O->>P: HTTP 请求<br/>X-WI-WIT: 身份令牌<br/>X-WI-WPT: 证明令牌
    P->>P: 五步校验
    P-->>O: 通过 → 处理请求 / 不过 → 拒绝

接收方(paysvc)收到后,做五步校验:

  1. X-WI-WIT 里的 JWT 格式正确、没过期、由可信签发者签名(签名能追溯到内部根)。
  2. X-WI-WPT 里的 JWT 格式正确、没过期。
  3. WPT 的 aud 确实是我(paysvc),不是发给别人的。
  4. WPT 的 wth 等于我手上这张 WIT 的哈希——两令牌确实是一对。
  5. WPT 是被 WIT 里那把公钥验证通过的(即:确实由持私钥的真身签的)。

五步全过,paysvc 就能百分百确定:此刻在跟它说话的,就是那个生产环境、跑在 us01 的订单服务实例。然后它再从 WIT 的 svc 字段里读出对方的身份信息,决定放不放行。

这套机制带来的好处,一次收齐:

  • 每个服务都确切知道对面是谁——不再靠“反正来自内网就信”的裸奔。
  • 密钥自动轮换,私钥永不离开签名的那台机器,一切都短命。
  • 没有长期共享密钥要管、要发、要担心泄露。

安全和可用性的双赢,基本就这么拿下了。

5. 授权:别让认证的进步,被授权的分歧拖住

认证解决的是“你是谁”,授权解决的是“你能不能干这件事”。这俩是两码事,但很容易被搅在一起吵。

我的态度很明确:

认证的巨大进步,不该被授权方案的分歧卡住。 先把“确切知道对方是谁”这件事落地,授权怎么做可以慢慢演进。

授权大致有两条路:

  • 分散式(各服务自理):接收方验完 WIT/WPT 后,自己拿 WIT 里的身份信息判断“这家伙我认不认、让不让”。跟很多团队今天的做法一样,改动最小,但全公司的授权规则散落各处,难统一、难审计。
  • 集中式(统一规则服务):把“谁能调谁”的规则收进一个专门的服务,它对外提供两类查询——“X 能调用哪些服务”“哪些服务能调用 X”。它只下发规则,不参与每次请求的验证(信任仍然由 WIT/WPT 各自锚定),所以不在热路径上:结果可以大力缓存,它偶尔抖动、延迟甚至短暂宕机,都不影响业务请求继续跑。代价是要多维护一个系统。

选哪条取决于你司规模和治理需求。但关键是先解耦:认证先上,授权按自己的节奏来。别为了争授权方案,把已经够得着的认证收益也一起搁置了。

6. 落地要改多少代码?比你想的少

最后回答那个最实在的问题:接这套,是不是要伤筋动骨?

如果你司本来就在大量用 JWT(前两篇也说了,这正是选 L7 的前提),那改动出乎意料地小——因为大部分动作你早就在做,只是换个来源和结构。

出站请求(你调别人):

  1. 私钥和 WIT 改从本机 agent 取(而不是从旧的密钥系统取),并接收轮换通知。
  2. 把要签的 JWT 组织成 WPT 的结构(和你现在签 JWT 的动作高度相似),放进出站请求头。
  3. 把 WIT 一并塞进请求头。

入站请求(别人调你):

  1. 加一段链式校验逻辑:验 WPT、验 WPT 与 WIT 的绑定、验签追溯到可信根(就是第 4 节那五步)。
  2. 不再去旧密钥系统要公钥——公钥现在就在 WIT 里带着。

其它基本原封不动。

如果想做得更漂亮(但工程量更大),可以写一个统一的网络中间件库(比如用 Rust),塞进所有应用,让业务代码彻底无感。不过这条更“正”的路,推动各团队接入的成本高,可以作为后话——先用最小改动把收益拿到手,再谈优雅。 这跟中篇“先摘够得着的果子”是同一个道理。

值得强调的连带红利:一旦切过去,那些为服务间认证而存在的长期密钥——各种对称/非对称签名密钥——大部分都能删掉了。管的密钥越少,睡得越香。

草案协议的落地边界

WIMSE 这类仍在演进的协议，文章最好明确区分三层内容：规范已经确定的概念、当前 draft 的字段和示例、作者为了说明流程而采用的简化实现。尤其是请求头名称、声明字段、签名算法和轮换行为，都应标注对应版本。

在真正落地前，至少做一次端到端失败测试：WIT 过期、WPT 与 WIT 不匹配、目标服务不匹配、时间窗口超限、签名密钥轮换中途请求到达。只展示成功路径会让读者低估协议接入的工程量，也会掩盖最容易出错的安全边界。

写在最后

三篇走下来,主线其实就一句话:先把“身份”当一等公民发出去,后面的认证,是顺着地基自然长出来的。

  • 身份:一张短命、可自证、云中立的证(SVID / WIT)。
  • 路线:先走能渐进、能马上见效的 L7,别死磕 mTLS 的合龙。
  • 协议:WIT 证明“我是谁”,WPT 证明“这条请求真的是此刻的我发给你的”,两个头、五步校验,冒充和重放全堵死。

这套东西最打动我的地方,不是它多先进,而是它顺——地基一打好,认证几乎是白捡的;代码改动小,还能顺手删掉一大批长期密钥。好的架构,往往不是加了多少东西,而是把原本拧在一起的东西拆开后,一切都变简单了。

行动清单(可抄)

  • [ ] 理清 WIT 与 WPT 的分工:一个长期公开证身份,一个临时私签证“此刻这条请求”。
  • [ ] 设计两个请求头(WIT / WPT)和接收方的五步校验,先在两个服务间打通。
  • [ ] WPT 的 exp 设到“略长于单次请求”即可(如 5 分钟),越短越安全。
  • [ ] 认证和授权解耦:先上认证,授权(分散式 or 集中式规则服务)按节奏演进。
  • [ ] 评估出站/入站的最小改动:私钥改从 agent 取、JWT 改成 WPT 结构、入站加链式校验。
  • [ ] 清点可以下线的长期签名密钥——这是最直接的安全与运维红利。
  • [ ] 记住协议仍是 IETF 草案,关注其演进,别在细节上过度定制。
