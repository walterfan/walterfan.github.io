deepseek-harness 有什么不一样：一个"没有核心"的 Agent 框架

Posted on 日 23 8月 2026 in AI

Abstract deepseek-harness 有什么不一样：一个"没有核心"的 Agent 框架

Category AI

Updated 2026-08-23

先说清楚一个词，免得后面都在云里雾里。harness 直译是"马具、挽具"，在 AI 圈里指的是"套在大模型外面那层东西"——模型只会吐字，真正让它能读文件、跑命令、记住上下文、一步步干活的那套骨架，就是 harness。你平时用的 Claude Code、Codex、Cursor，模型是发动机，harness 才是让这台发动机装上轮子、方向盘和刹车的底盘。

DeepSeek 最近开源了自己的 harness，叫 dsh（deepseek-harness），README 上就一句口号：Everything is a Plugin（一切皆插件）。第一眼我是有点不以为然的——插件化谁不会喊？现在哪个框架不带个 plugin 系统。真正让我坐下来读文档的，是它那句更狠的补充：模型适配器、工具注册表、会话日志、乃至 agent 主循环本身,都是插件,都能从配置里换掉。没有一个需要打补丁的特权核心（no privileged core to patch）。

这句话如果你也做过后端、也维护过带插件系统的框架，应该会跟我一样心里"咯噔"一下——因为"特权核心"正是我们踩过最多坑的地方。这篇就讲清楚：dsh 到底跟别家不一样在哪，这种不一样值不值,以及它的代价藏在哪儿。

  • 它不一样的不是功能多，而是架构范式：从"有核心 + 插件"变成"连核心都是插件"。
  • 好处是任何能力都能被替换、被重组；代价是没有一个稳定的地基可以依赖。

我们都被"特权核心"坑过

先讲个我熟悉的场景。做过带插件的系统的人，大概都经历过这样一天：框架有个"核心"（core），核心之外留几个扩展点（hook），插件挂在扩展点上干活。设计当天这套边界看着特别清爽——核心稳如泰山，插件自由发挥。

然后需求来了。产品要一个核心没预留扩展点的行为改动，比如"这类会话的鉴权流程走另一套"。扩展点不够用，怎么办?三条路：改核心（那核心就不"稳"了，还得全量回归测试）、绕过核心硬 patch（那就埋了颗雷，下次核心升级它就炸）、或者跟产品说"这个做不了"（那你就成了那个挡路的人）。

这就是"特权核心"的原罪：核心比插件高一等，插件只能在核心恩准的地方伸手。核心没想到的事，插件就做不了；核心想改的时候，插件只能跟着遭殃。我们习惯了这种不对等，甚至觉得理所当然——总得有个"主心骨"吧？

dsh 的回答是：不，主心骨也可以是块积木。

"一切皆插件"到底皆到什么程度

口号谁都会喊，关键看它落到哪一层。我把 dsh 文档里那张"能换什么"的清单翻译过来，你感受一下颗粒度：

能换的东西 在别家通常是什么 在 dsh 里是什么
模型适配器（换个大模型） 配置项，偶尔要改代码 一个插件，注册到 ctx.llm
工具（给 agent 加能力） 核心提供的注册接口 一个插件，注册到 ctx.tools
会话日志（记录发生了什么） 核心内置，基本动不了 一个插件，ctx.sessions
沙箱（隔离命令执行） 核心里写死的一段逻辑 一个可换的 backend
agent 主循环（一步步干活的那台驱动） 核心中的核心，碰不得 一个插件，ctx.agentLoop

前面几行你可能觉得"也就那样"，很多框架的模型和工具确实能换。但看最后一行——连 agent loop 都是插件。agent loop 是什么？就是那个"发一次模型请求、解析出要调用哪些工具、调完再决定要不要继续"的循环。在几乎所有 harness 里，这就是最神圣不可侵犯的核心，你能往里塞 hook，但你换不掉它本身。

dsh 里它只是 core/agent-loop 这么个包，实现了 Agent 接口而已。你想换一套完全不同的驱动逻辑？写个新插件挂上去，把旧的卸下来。没有"核心"这个特权阶层，只有一堆平权的插件挂在同一棵树上。 这背后是一个叫 Cordis 的框架：所有插件往一个共享的 context（上下文，可以理解成一块公共布告栏）上贡献服务、事件和"可撤销的副作用"，插件卸载时，它当初挂上去的东西会自动收回，不留残渣。

一句话概括这个范式的转变：

别家是"核心 + 插件"，dsh 是"插件 + 插件 + ... 其中一个恰好叫循环"。 没有谁天生高一等，这才是它"不一样"的真正含义。

换一个零件，为什么能带动整个产品

光是"什么都能换"还不够惊艳，真正巧妙的是 dsh 的能力接缝（capability seam）设计。这个词有点抽象，我用装修打个比方。

假设你家所有用水的地方——厨房、卫生间、阳台——都接在同一套水路接口上。这套接口是"约定"：水从这个口进、那个口出。现在你想把自来水换成净化水，你不用挨个改水龙头、改花洒、改洗衣机进水管，你只要在总接口上换一个净化模块，全屋的出水就都变了。

dsh 的接缝就是这套"总接口"。文档里举了个例子特别能说明问题：文件系统和子进程这两个能力，共享同一个"执行世界"。所以当你把它们的 provider（提供方）指向一个远程沙箱，Bash 命令、PTY 终端、LSP（代码语言服务）会一起搬过去——你不用给每个工具单独写一个"远程版本"。换一个 provider，整个产品的行为就跟着变了。

这就是"接缝"比"插件"更进一步的地方。普通插件系统是"我加一个新功能"；接缝是"我换一种实现，所有用到它的地方一起变"。对做架构的人来说，这是两种完全不同的杠杆。

一切都从一份日志里长出来

还有一个我觉得特别克制、也特别聪明的设计，叫 model-visible means logged（模型能看见的，就必须被记下来）。

dsh 有一条会话日志（session log），是只追加的（append-only，只往后加、不改前面的）。关键规则是：任何最终会进到模型请求里的东西，都必须能从这条日志里重建出来，而且运行时有个断言（assertion，一段"不满足就报错"的自检代码）死死盯着这条铁律。

这个约束看着朴素，威力却很大。因为整个产品的一堆能力——会话的分叉（fork）、恢复、生成对话记录、遥测、持久化——全都是从这一条日志派生出来的，而不是各写各的状态。你想给 agent 加一种新的"模型可见的输入"？规则逼着你：去扩展日志的事件类型，然后从日志渲染出来。不许走后门。

我做后端这些年，最头疼的从来不是功能不够，而是状态散落各处、没有单一事实源（single source of truth）。同一份数据，缓存里一份、内存里一份、库里一份，出了 bug 你都不知道该信哪个。dsh 这条"模型能看见的必须被记下来"，本质上是把"上下文"这件事强行收敛到一个唯一来源。这种自律，是老工程师才写得出来的规矩。

那么，代价在哪儿

夸到这儿，得泼盆冷水了——天下没有免费的架构。我要是只讲好话，那这篇就成软文了。

第一，没有稳定地基，也意味着没有稳定地基。 特权核心讨人嫌，但它有个好处：它稳定，你可以放心依赖。当一切皆插件、连主循环都能换，你写的每个插件都得考虑"我依赖的那个能力，会不会哪天被人换成另一套实现"。自由的另一面是没有承诺。这也是为什么 dsh 现在的 README 里明明白白写着：处于开发者预览阶段，未来会有破坏兼容性的变更（compatibility-breaking changes）。这不是谦虚，是"一切皆插件"这个选择的必然。

第二，心智负担上移了。 "核心 + 插件"的模型虽然不够灵活，但它好懂——新人一看就知道"哦，核心管这些，我在这几个 hook 里写就行"。而在一棵所有节点平权的插件树里，你得先理解 Cordis 的那套 context、事件、接缝的抽象，才知道自己该把代码挂哪儿。灵活性从来不是白给的，它把复杂度从"改核心"转移到了"理解整棵树"。

第三，它现在还很早。 18 万颗星、快速迭代、开发者预览——这几个词放一起，翻译过来就是：值得学习它的设计，但先别把生产系统押上去。

一句话：

dsh 的"不一样"是一种架构上的激进，激进的东西往往先值得读，再谨慎地用。 先偷它的思路，别急着搬它的代码。

总结：真正的插件化，是连"核心"都敢拆

回到最开始那个问题——deepseek-harness 到底哪里不一样？

不在于它工具多、模型强，那些别家也在追。它真正不一样的，是把"一切皆插件"这句被喊烂的口号，贯彻到了连 agent 主循环、连"核心"这个概念本身都拆掉的程度。别家是"有核心，核心之外皆插件"；它是"没有特权核心，其中一个插件恰好叫循环"。

对我这种被"特权核心"坑过的老程序员来说，这里面有个朴素的启发，跟写不写 agent 其实没关系：

你系统里那个"谁都不许动"的核心，往往不是因为它真的不该动，而是因为你当初没敢把它设计成可以被换掉。 哪天你也想给自己的系统留条后路，不妨先问一句——如果这块"核心"也只是一个插件，会怎么样？

想上手的，npx @deepseek-ai/dsh web 一条命令就能在本地把它跑起来，边跑边读文档，比干看强。
