用 FreeSWITCH + MySQL 构建异地双活的音视频服务

大纲

展开看看
  • 一句话：异地双活的难点不在 FreeSWITCH，而在 MySQL 的跨机房写入和媒体流的状态同步。信令、数据、媒体三层各有各的一致性模型，用一套方案硬套全部就是灾难。
  • 先定义双活：两个机房同时在线接客，不是主备。关键指标是单机房整体失效时，新呼叫能否就近接管、在途呼叫丢多少。
  • 三层拆开看：信令（SIP/注册/路由）、数据（账户/计费/CDR）、媒体（RTP 流）。每层的 CAP 取向不一样，强行统一就是灾难。
  • 信令层可以 AP：把 FreeSWITCH 退成无状态媒体工人，注册和路由状态外置，边缘用 OpenSIPS 做 anycast + 集群，任一机房挂了重新注册即可。
  • 数据层必须分 CP 和 AP：账户余额、并发额度这类"扣减"操作要强一致（CP），CDR、话单这类"只追加"的可以最终一致（AP）。一个 MySQL 集群里塞两种需求是第一个大坑。
  • 跨机房 MySQL 的三种真实选择：半同步主从（一写一读）、Group Replication 多写、按业务分片各自为主。各有各的代价，没有银弹。
  • 媒体层只能就近锚定：RTP 流的"双活"本质是伪命题，一路通话的媒体在哪个机房建立就钉死在哪，切机房等于重建通话。能做的是故障时快速重建，不是无缝漂移。
  • 落地顺序：先无状态化信令、再拆分数据一致性等级、最后用 GSLB + 健康检查把流量在机房间调度。别一上来就追求"零丢失"。

接着上一篇给 FreeSWITCH 集群配两个搭档往下走。那篇解决的是单机房内怎么把 FreeSWITCH 扩到上万路。这篇要回答的问题更狠一档：

两个机房，相隔上千公里，要同时在线接客。一个机房整体失效（断电、断网、光缆被挖断），业务还能跑。这事怎么做？

很多人一听"FreeSWITCH 异地双活"，第一反应是去研究 FreeSWITCH 怎么做集群、怎么同步会话。方向错了。FreeSWITCH 这层信令早有成熟的无状态做法，真正把人拖进泥潭的是另外两处：跨机房的 MySQL 怎么同时写还不打架，以及活跃通话的媒体流钉死在建立它的那个机房、根本切不过去。

异地双活不是一个一致性问题，是三个。 信令、数据、媒体，三层的 CAP 取向完全不同——信令可以 AP，计费必须 CP，媒体只能就近锚定。想用一套方案把三层一起"双活"掉的人，最后都会在某一层上栽跟头。

  • 这篇默认你做过音视频/通信，SIP、RTP、主从复制这些术语直接用。
  • 下面的配置和参数都是示意，用来说明思路，不是可以直接抄进生产的模板。

先把"双活"定义清楚，别偷换概念

异地双活（geo active-active）这个词被用得很滥，先对齐定义，不然后面全是鸡同鸭讲。

双活不是主备。 主备（active-standby）是一个机房干活、另一个机房空转待命，故障时切过去。双活（active-active）是两个机房同时接客，平时就各自承担一部分真实流量。主备好做，双活难在"同时写"。

判断一套方案到底是不是双活，就看一个反直觉的指标：平时两个机房的写流量占比是不是都显著大于零。 如果 B 机房平时写入量约等于零，只是热备着，那它是伪双活——真出事的时候，那条从没被真实流量压过的写路径，大概率会在切换瞬间暴露一堆问题。

对音视频服务，衡量双活成色的还有两个硬指标：

  • 新呼叫接管时间：一个机房整体失效后，打进来的新呼叫多久能被另一个机房正常接起。这个指标好做，几秒内可达。
  • 在途呼叫存活率：失效瞬间，正在通话中的那些呼叫，有多少能活下来。这个指标，对音视频来说基本是零——后面会讲为什么这是媒体层的物理限制，不是你方案烂。

把预期摆正：异地双活保的是"业务不中断地接新客"，不是"一通电话打一半机房没了还能不断"。 后者在单一通话层面做不到，谁跟你承诺媒体流无缝漂移，要么是没做过，要么是把"重连"包装成了"不中断"。

三层拆开看：一张图说清楚难点在哪

把一个音视频呼叫从接入到落账，拆成三层，每层问一句"它的状态能不能跨机房同时写"，难点就浮出来了。

层 典型组件 状态是什么 跨机房诉求 CAP 取向
信令层 OpenSIPS / FreeSWITCH / 注册 谁在线、呼叫往哪路由 任一机房能接管新呼叫 AP：可短暂不一致，重注册即恢复
数据层（扣减） MySQL 账户/余额/并发额度 钱、额度这类"减下去不能超发"的量 两地同时扣不能超卖 CP：宁可拒绝，不可错扣
数据层（追加） MySQL CDR/话单/日志 通话记录这类"只往后加"的量 两地都能写，最终对齐 AP：最终一致即可
媒体层 RTP / rtpengine 一路通话的实时音视频流 （做不到跨机房漂移） 就近锚定：建在哪个机房就钉在哪

这张表是全篇的骨架。同一个"异地双活"需求，落到这四行上是四种完全不同的工程——信令要的是能重建，扣减数据要的是强一致，追加数据要的是能合并，媒体要的是能快速重连。 谁要是用"搭一套 MySQL 主主复制"一招通吃这四行，哪一行都做不好。

下面逐层拆。

信令层：让 FreeSWITCH 变成"可抛弃的媒体工人"

信令层是最好办的，因为 SIP 本身就为"重注册"而设计。

核心做法上一篇讲过，这里只说和"异地"相关的部分：把 FreeSWITCH 退成无状态的媒体工人，把"谁在线""呼叫往哪路由"这些状态全部外置。 FreeSWITCH 节点本身不存任何跨机房要共享的东西，它挂了就挂了，流量重新路由到别的节点——哪怕是另一个机房的节点。

三件事让信令层"异地可接管"：

  • 注册状态外置且可跨机房读。 终端注册信息（AoR → Contact 的映射）不存在某台 FreeSWITCH 的内存里，而是存到一个两地都能访问的地方。OpenSIPS 的 usrloc 配合 clusterer 做分布式位置服务，或者直接落到一层共享存储。终端在 A 机房注册，B 机房也看得见它在线。
  • 边缘用 anycast / GSLB 分流。 终端通过一个统一的 SIP 接入域名进来，DNS SRV + GSLB（全局负载均衡）按健康状况和地理就近，把它导向某个机房的 OpenSIPS。A 机房的 OpenSIPS 整体不可达时，DNS 层面把新请求切到 B。SIP 终端会在注册超时后重注册，自然落到 B。
  • 路由决策无状态。 OpenSIPS 做路由时，从外置的位置服务和数据库里读信息，不依赖"上一跳是哪台 FreeSWITCH"这种进程内记忆。

信令层做 AP 的底气，来自 SIP 的重注册语义。 终端和服务端的注册关系是有租期的（Expires），到期必须续。这意味着任何一次机房切换，最坏情况也就是"等一个注册周期"就自愈。你不需要跨机房实时同步每一条注册的毫秒级状态，只要保证新的注册能落到活着的机房即可。

这就是为什么信令层能接受 AP：短暂的不一致（B 机房还不知道某终端刚在 A 掉线）不会错，只会慢一拍，而 SIP 的重试机制会把这一拍补回来。

数据层：第一个大坑，把"扣减"和"追加"混在一个一致性等级里

信令搞定后，真正的硬骨头来了。MySQL 跨机房双活，最常见的翻车姿势是：把所有表塞进同一个复制拓扑，用同一个一致性等级伺候。

要害在于，音视频业务的数据天然分两类，它们对一致性的要求是相反的：

  • 扣减型（CP）：账户余额、预付费额度、并发呼叫数上限、License 席位。这类数据的共同点是"减下去不能超"。两个机房同时给同一个账户扣费、同时占用最后一个并发名额，如果不是强一致，就会超卖——余额扣成负数、并发突破上限。这类必须 CP：宁可在网络分区时拒绝服务，也不能错扣。
  • 追加型（AP）：CDR（话单）、通话日志、事件流、录音索引。这类数据只往后加，不存在"两地同时改同一行"的冲突。A 机房写 A 的话单，B 机房写 B 的话单，事后合并即可。这类做 AP 最舒服：两地都能本地写，最终一致。

把这两类强行统一，结果是两头不讨好：

  • 如果为了 CDR 的写入性能，整库都用 AP（异步复制），那扣减型数据就有超卖风险——网络一抖，两地各扣各的。
  • 如果为了余额安全，整库都用 CP（同步复制跨机房），那每一条 CDR 的写入都要等对端机房 ACK，几十毫秒的跨机房 RTT 直接拖垮话单写入吞吐，高并发时话单堆积。

正确的切法是按数据性质分治，这是整篇最想让你记住的落地原则：

数据类型 例子 跨机房策略 冲突处理
扣减型 余额、并发额度 单点强一致：全局只有一个"权威写入点"，或用分布式锁/租约 不允许冲突，分区时拒绝
追加型 CDR、日志、事件 两地各自本地写，异步双向同步 天然无冲突，按时间合并
配置型 费率、路由规则 变更低频，单写多读，异步下发 以写入点为准
会话型 注册、在线状态 不进 MySQL，放缓存/位置服务 靠 SIP 重注册自愈

把这张表刻进脑子：你不是在为"音视频业务"选一致性，你是在为每一类数据分别选。

跨机房 MySQL 的三种真实选择，没有银弹

扣减型数据需要跨机房的强一致写，这是整套方案里最硬的约束。MySQL 层面有三条真实可走的路，各有各的代价。（不想用 MySQL、想换 Redis / NewSQL / Cassandra / etcd 的，见姊妹篇异地双活不用 MySQL 行不行。）

方案一：半同步主从，一写一读（最稳，但不是真双活）

A 机房主库，B 机房从库，rpl_semi_sync 半同步复制。所有写走 A，B 只读。

# 示意配置，非生产模板
# 主库 (A 机房)
rpl_semi_sync_source_enabled      = ON
rpl_semi_sync_source_timeout      = 1000   # 1s 内对端没 ACK 就退回异步
rpl_semi_sync_source_wait_for_replica_count = 1
  • 优点：强一致性最好保证，扣减绝不超卖；运维模型简单，故障切换成熟。
  • 代价：它本质是主备，不是双活。 B 机房的写能力是零——所有扣减型写入要跨机房打到 A，B 机房的用户体验里，每一次扣费都带着一个跨机房 RTT。而且 A 整体挂掉时，提升 B 为主（failover）这一步要人工或自动决策，有切换窗口。
  • 什么时候用它：如果你的扣减型写入频率不高（大部分音视频业务，真正的"扣钱"动作远少于信令和媒体包），这个方案的跨机房 RTT 代价可以接受，稳定性换来的省心很值。别为了"看起来像双活"而放弃它的简单。

方案二：Group Replication 多写（真双活，但冲突是你的）

MySQL Group Replication（MGR）多主模式，两地都能写，组内用 Paxos 类协议做冲突检测。

  • 优点：两地真的都能写，是名副其实的多活。
  • 代价：跨机房的 MGR 对网络延迟极其敏感。 每一个事务提交都要在组内达成多数派共识，机房间 RTT 几十毫秒的话，写事务延迟会显著放大，吞吐掉得厉害。更麻烦的是写冲突：两地同时改同一行，MGR 会让后提交的那个事务回滚报错，这个错误要你的应用层接住并重试——对账户扣减这种，重试逻辑写不好就是对账噩梦。
  • 什么时候用它：两个机房网络质量很高（专线、RTT 低且稳定），且你有能力在应用层处理事务回滚和重试。冲突不会消失，MGR 只是把冲突从"数据错乱"变成"事务报错"，接不住它的还是你。

方案三：按业务/用户分片，各机房为自己的分片做主（最务实的双活）

把用户或账户按某个维度（地域、uid 取模）分片，每个分片在一个机房是主、另一个机房是从。A 机房是华东用户的主库、华南用户的从库；B 机房反过来。

  • 优点：规避了"两地同时写同一行"——因为同一个用户的写永远只落在一个固定机房。既获得了双活的写入分担（两地都在写，只是写不同分片），又不用处理跨机房写冲突。
  • 代价：分片键的选择是一次性的重大决策，选错了后面迁移极痛。 而且当一个机房挂掉，它负责的那些分片要临时"升格"对端的从库为主，切换期间这部分用户的写入有短暂窗口。跨分片的事务（比如 A 用户给 B 用户转额度）会变复杂。
  • 什么时候用它：大多数要"真双活"又扛不住 MGR 跨机房延迟的场景，这是性价比最高的一条。它的哲学是"不解决跨机房写冲突，而是从设计上让它不发生"。

一句话收口这三条：

跨机房强一致写的代价是物理定律收的税，不是 MySQL 的 bug。 光速限死了跨机房 RTT，强一致就必然等这个 RTT。你只能选"在哪一层、为哪些数据"交这个税——交给半同步的所有写、交给 MGR 的每个事务、还是交给分片方案里偶尔的跨分片操作。想一分钱税都不交又要强一致又要双活，没有这种方案。

媒体层：双活是个伪命题，能做的是快速重建

讲到媒体层，先泼一盆冷水：一路活跃通话的媒体流，做不到跨机房无缝漂移。 这不是方案的问题，是 RTP 的物理现实。

原因很直接。一路通话的 RTP 流，在建立的那一刻就锚定了一组东西：协商好的媒体 IP 和端口、SRTP 的加密上下文、ICE 的候选对、rtpengine 分配的转发端口。这些状态是连接级的，分布在建立这路通话的那个机房的 rtpengine 和 FreeSWITCH 里。想把它"同步"到另一个机房，等于要实时复制一个加密 UDP 流的全部运行时上下文——每秒几十个包的状态，跨机房几十毫秒延迟地同步——技术上即使硬做，同步延迟也早就超过了音视频可接受的抖动窗口。

所以媒体层的"异地双活"要重新定义：不是让一路通话在机房间无缝漂移，而是在一个机房失效时，让受影响的通话尽快在另一个机房重建。

实务上就是三条：

  • 媒体就近锚定。 终端接入哪个机房，这路通话的 RTP 就在那个机房的 rtpengine 上建立、就在那个机房的 FreeSWITCH 上处理。不要让一路通话的两条腿横跨机房——那不仅没有双活价值，还白白增加一个跨机房 RTT 的音频延迟。
  • 故障即重建，别幻想续命。 A 机房挂了，上面的在途通话就是丢了。接受它。真正要做好的是：终端检测到媒体中断后（RTP 超时、ICE 失败），能快速重新发起呼叫，这次被 GSLB 导向 B 机房，在 B 重建一路新通话。用户体感是"电话断了一下，重拨/自动重连后恢复"，不是"没断"。
  • 把"重建快"这件事做扎实。 这才是媒体层异地可用性的真战场：重注册要快（信令层已经保证）、GSLB 探活要灵敏（别让终端还在往死机房打）、客户端要有自动重连逻辑（检测到媒体断流主动重建，而不是等用户手动重拨）。

媒体层比的不是"不断"，是"断了多久能回来"。 把目标从虚无缥缈的"零丢失"换成实在的"秒级重建"，整个方案立刻从玄学落回工程。

落地顺序：别一上来就追零丢失

把三层拼起来，一套能真正跑的异地双活，落地有个推荐顺序。逆着这个顺序做，会在错误的地方耗光预算。

  1. 先把信令层无状态化。 把 FreeSWITCH 退成媒体工人，注册和路由状态外置到两地可读的位置服务。这一步做完，你已经能扛单节点故障，并且为跨机房打好地基。顺序上它必须最先，因为它是另外两层的前提。

  2. 再按数据性质拆分一致性等级。 把扣减型和追加型数据分开。扣减型选三条 MySQL 方案之一（多数业务从半同步主从起步就够），追加型做两地本地写 + 异步合并。这一步是整篇的核心价值，也是最容易被跳过的一步——跳过它，你的双活迟早在一次网络分区里暴露超卖或对账问题。

  3. 用 GSLB + 健康检查做机房级调度。 统一接入域名，DNS SRV + 全局负载均衡，按机房健康状况和地理就近分流。健康检查要覆盖到"能不能接新呼叫"这个业务级信号，而不只是"端口通不通"。

  4. 最后打磨故障时的重建速度。 客户端自动重连、GSLB 探活灵敏度、重注册周期调优。把"在途呼叫丢了之后多久恢复"压到秒级，这就是媒体层异地可用性的全部。

一句话：

先保证"新客能就近接起"，再优化"老客断了快点回来"，永远不要承诺"老客不断"。 把工程预算花在能兑现的目标上，而不是物理上做不到的"媒体无缝漂移"。

总结：异地双活是三个一致性问题，不是一个

回到开头那条判断：FreeSWITCH 从来不是异地双活的难点。 它这层信令早有无状态的成熟做法——退成媒体工人，状态外置，重注册自愈，照抄即可。

真正要你动脑子的是另外两层，而且它们的答案是相反的：

  • 数据层要你把"扣减"和"追加"分开——前者 CP、宁拒绝不错扣，后者 AP、两地本地写最终合并。跨机房 MySQL 没有银弹，半同步主从、MGR 多写、业务分片，你是在选"在哪一层交光速这笔税"。
  • 媒体层要你认清 RTP 流无法跨机房漂移，把目标从"不断"换成"秒级重建"。

一套方案通吃三层的人，会在某一层栽跟头；把三层拆开、各给各的一致性模型的人，才能做出真正扛得住机房级故障的双活。

下次有人跟你说"我们 FreeSWITCH 做了异地双活"，你可以问他三个问题：你的 MySQL 扣减型数据怎么防超卖？CDR 怎么两地合并？机房挂了在途通话丢多少？ 答得上这三问的，是真做过；答不上的，大概率是把主备叫成了双活。
